# 3단계 지속음·음높이 개선 준비

작성일·피드백 재검토일: 2026-10-02 · 조사 기준: `92060b4`

**이 문서는 구현 전 조사·준비 기록이다. 이후 사용자의 구현 요청에 따라 수정했으며, 최종 결정과 검증 결과는 [구현 ADR](../decisions/2026-10-02-sustain-source-calibration.md)에 기록했다. 아래 수치는 수정 전 기준선이다.**

이번 수정의 핵심은 **페이드에 쓰는 원음의 안정성과 페이드 적용 후 반복 길이를 함께 보장하는 것**이다. 접합 수정·게인 한도 분리·가야금 처리를 먼저 하고, 실제 샘플과 보정값을 연결하는 소스 전환 정책을 정한 뒤 최종 음정·음량을 재측정한다. 아래의 수정 방식은 구현 계획이며, 개선된 소리를 이미 적용·검증했다는 뜻은 아니다.

## 원하는 결과와 확정한 기준

- 관악기와 활로 켜는 현악기: 같은 높이로 이어 그린 한 획은 하나의 지속음으로 들린다.
- 가야금: 한 번 뜯은 소리가 자연스럽게 잦아든다. 수평선을 그리는 동안 반복해서 뜯거나 다음 원음이 나오면 안 된다.
- 피아노도 자연 감쇠를 원한다는 사용자 답변이 있었으나, 현재 앱의 13종 악기에는 피아노가 없다. 악기를 추가하는 작업은 포함하지 않는다.
- 그리는 동안, 전체 듣기, 일시정지 후 재개, 플레이헤드 위치부터 새로 재생, 내보내기에서 같은 음높이 기준을 쓴다. 일시정지 재개와 위치를 옮겨 새로 재생하는 것은 별도 경로로 검사한다.
- 음의 연결을 개선해도 왼쪽 음높이 칸과 소리가 어긋나면 안 된다. 자연스러운 비브라토·시김새와 지속적으로 틀어진 중심 음정을 구분한다.
- 자유 그리기의 가로 좌표=작품 시간 규칙을 유지한다. 제자리에서 오래 누르는 미리듣기와, 가로로 길게 그려 저장한 음의 길이는 별개다. ‘음악에 맞춰 그리기’에서는 누르는 동안 시간에 따라 획이 기록된다.

## 이번에 확인한 범위

로컬 HTTP 서버에서 현재 스크립트와 MP3를 그대로 불러왔다. 별도 Chrome 검증 세션의 실제 Web Audio `OfflineAudioContext`로 선율을 렌더했다.

- 서양 8종 × 15칸 + 국악 5종 × 10칸 = **170칸**.
- 각 칸의 수평 획에 대해 드로잉 미리듣기 6초와 저장 획 재생 6초를 각각 렌더했다. 저장 획 재생은 끝 여운을 포함해 6.5초까지 수집했다.
- 디코드·측정은 모노 22,050Hz. 미리듣기는 `_createSampleLivePreview`, 저장 획은 `scheduleSampleStrokes`를 사용했다. 저장 획 측정은 최종 마스터/리미터 앞의 선율 경로다.
- 바이올린·단소·가야금은 실제 캔버스 포인터 입력도 확인했다. 자유 그리기에서 수평 이동, 음악에 맞춰 그리기에서 약 1.5초 제자리 유지 모두 재생 소스가 한 번만 생성됐고 손을 떼면 미리듣기가 해제됐다.
- 가야금의 ‘도’는 30초 미리듣기로 추가 검사했다.
- 기존 `npm test`: **333개 통과, 실패 0개**.

피드백 검토에서는 클로드의 저장소 밖 `xv/` 스크립트를 읽고 별도 임시 폴더에 복사해 다음을 다시 실행했다.

- 현재 엔진을 Node `vm`으로 로드하고 ffmpeg 48,000Hz 모노 디코드로 170칸의 계획·버퍼를 생성: 좌표 불일치 0, 수평 획 소스 모두 1개.
- NumPy 크로스페이드와 엔진이 만든 Float32 버퍼의 최대 차이 **0.0** 확인 후 두 대안의 접합점을 비교.
- 음 이동 시 예약되는 게인과 플레이헤드 시작 위치별 샘플 선택을 실제 엔진 함수로 확인.
- 기존 분석 JSON의 음정 초과 건수를 재집계하고, 가야금 10칸의 원본 감쇠·다음 발음을 48kHz PCM에서 추가 측정.
- 클로드의 넓은 범위 YIN 결과와 배음 확인 자료도 검토. 기존 분석기의 예상 음 주변 탐색만으로는 옥타브 오류를 독립적으로 배제할 수 없다는 한계를 반영.
- 후속 피드백 검증: 160칸의 반복 시작 전 재료·페이드 후 길이를 재계산하고, 실제 MP3를 디코드해 단소 라→미의 두 엔진 경로를 비교했다. 크로스페이드 ① 우선 방침을 아래 공통 규칙으로 대체했다.

48kHz VM 검증은 실제 샘플과 엔진 계산을 검사하지만 브라우저의 오디오 그래프를 렌더한 검사는 아니다. 22.05kHz Chrome 검증과 서로 보완한다. 실제 장치의 `AudioContext.sampleRate`를 기록하고, 구현 후 Chrome 44.1/48kHz에서도 확인한다. ffmpeg 48kHz 한 가지를 모든 장치의 정답으로 삼지 않는다.

**아래 ‘안정/우선 점검’은 파형·음량 측정에 따른 분류다. 사람의 청감 비교를 마친 품질 판정은 아니다.** 전체 믹스, 최종 WebM, 170칸의 실시간 30초 유지, 모든 음 사이 이동은 후속 구현 검증 대상이다.

## 악기별 구분

수치는 실제로 반복하는, 크로스페이드 적용 후 버퍼를 50ms RMS 창으로 측정한 **루프 내부 최대–최소 음량 차**다. ‘평균’은 그 악기의 표시 음 전체 평균이고 ‘최대’는 가장 변화가 큰 한 음이다. 악기 사이의 절대 음량 비교가 아니다. 자연스러운 연주 강약도 포함하므로 이 수치 하나로 소리 품질을 단정하지 않는다.

이 표는 최초 Chrome 22.05kHz 측정값이다. 48kHz 재검증에서 악기별 평균은 약 ±0.2dB 안에 들었으나, 오보에의 최대는 **9.2 → 6.2dB**로 달라졌다. 디코드·샘플레이트에 따른 경계 선택 차이를 섞어 단일 최대값을 보편적 수치로 인용하지 않는다. ‘음량 변화가 비교적 작다’는 분류도 접합점이 정상이라는 뜻은 아니다.

현재 구현의 고정 비율 루프는 대체로 원음의 28~78%다. 바이올린 최저 솔은 별도 비율을 사용하고, 포락선 기반 자동 검출은 **더블베이스에만** 적용한다. 기존 [지속음 ADR](../decisions/2026-07-02-sustain-loop-stable-region.md)의 단계적 확대가 아직 끝나지 않은 상태와 일치한다.

## 원인별 조사 결과

### 1. 같은 음을 매번 새로 재생하는 것이 수평 획의 주된 원인은 아니다

170칸 모두 저장한 한 수평 획은 한 개의 샘플 소스로 예약됐다. 대표 3종의 실제 드로잉 입력에서도 같은 높이의 이동/유지 중 소스가 재생성되지 않았다.

따라서 우선 살펴볼 곳은 획 분할보다 **이미 재생 중인 음원 안의 반복 구간과 그 경계**다. 다른 높이로 움직일 때와 로딩이 덜 끝났을 때의 동작은 별도 경우로 검사한다.

관련 코드: `js/audio-engine.js`의 `liveDrawingMove`, `scheduleSampleStrokes`, `_scheduleSampleSourceNode`; `js/audio-plan.js`의 `strokeSegmentsForPlan`.

### 2. 소리가 줄어드는 꼬리가 반복되면 음량도 주기적으로 출렁인다

바이올린·비올라에 특히 큰 변화가 측정됐다. 기존 문서도 같은 원인을 기록하고 있다. 파일 길이의 일정 비율만으로는 모든 음원의 지속 구간을 찾을 수 없다.

다만 자동 검출 명단을 한꺼번에 넓히는 것만으로 해결됐다고 판단하지 않는다. 원음의 몸통 안에서도 비브라토나 강약이 다르고, 너무 짧은 구간은 음색이 빠르게 반복된다. 실제 재생 속도에 따라 들리는 루프 길이도 달라진다.

관련 코드: `sampleSustainLoopRegion`, `sustainLoopHint`, `autoSustainLoopHint`, `continuousSustainPlan`; `js/music-core.js`의 `findStableLoopRegion`.

### 3. 크로스페이드의 혼합 구간과 되돌아갈 위치가 맞지 않는다 — 확정 결함

반복 시작을 S, 끝을 E, 페이드 길이를 F라 하면, `createCrossfadedSustainBuffer`는 끝의 `[E−F, E)`에 **`[S, S+F)`를 섞은 다음 S로 돌아간다.** 끝에서 이어지도록 만든 소리는 S+F 직전인데, 실제 다음 위치는 S다. 이 불일치가 반복 접합점을 깨뜨린다.

48kHz 재실행 결과는 다음과 같다. ‘꺾임’은 이산 2차 차분의 절댓값이며, 접합점에서는 `|x[S] − 2x[E−1] + x[E−2]|`로 계산했다. 루프 내부의 같은 지표와 비교했다.

| 방식 | 접합점 꺾임이 내부 최댓값보다 큰 칸 | 접합점 / 내부 99백분위의 중앙값 |
| --- | ---: | ---: |
| 현재: `[S, S+F)`를 섞고 S로 복귀 | 148 / 160 | 9.47배 |
| 대안 ①: `[S−F, S)`를 섞고 S로 복귀 | 0 / 160 | 0.21배 |
| 대안 ②: 현재 혼합을 유지하고 S+F로 복귀 | 0 / 160 | 0.27배 |

**①을 일률적으로 우선하는 방침은 철회한다.** 위 표는 접합점의 개선만 보여 주며, 섞는 재료의 안정성을 보증하지 않는다. 자동 검출의 S는 안정 구간의 시작에 가까워 그 앞에 무음·어택이 들어가는 경우가 많다. 파일 범위에 맞추려고 F를 줄이는 것만으로 그 재료가 안정되지는 않는다.

48kHz 원본 PCM으로 확인한 결과:

- 더블베이스 15칸 중 **14칸**은 `[max(0,S−F),S)` 전체 RMS가 원래 루프 본체 RMS보다 3dB 이상 작았다. 이 앞 구간을 20ms 창으로 나눠 최저값을 비교하면 본체 대비 **약 −66~−5dB**다. 어택 앞의 작은 소리를 루프 끝에 다시 섞는 문제가 확인됐다. 두 수치는 평균과 최저 창이라는 서로 다른 지표다.
- 더블베이스 **5칸은 S 자체가 F보다 짧다.** 앞 구간을 파일 시작까지 줄여도 안정한 재료가 생기는 것은 아니다.
- 고정 비율 145칸도 앞 구간의 음량을 검사해야 한다. 앞 구간의 최대 20ms RMS와 본체의 20ms RMS 중앙값을 비교하면 **13칸이 +3dB 초과**다. 전체 구간 RMS끼리 비교하면 7칸으로 달라지므로, 개수와 함께 비교 창·통계를 명시한다. 특히 기존 루프가 감쇠 구간에 걸린 문제는 이후 지속 구간 재선정으로 다룬다.

**두 대안을 다음 필요조건으로 통합한다.** 검증된 안정 구간을 `[A,B)`, 최종 복귀점을 R이라 할 때, 섞는 앞 재료 `[R−F,R)`와 끝 재료 `[E−F,E)`가 모두 안정 구간 안에 있어야 한다. 앞 재료를 끝에 섞고 R로 돌아간다. 개념적으로 `R = max(S, A+F)`로 정하되 끝과의 간격·페이드 길이·위상 정렬 후에도 범위를 다시 검사한다.

- S 앞에 충분한 안정 재료가 있으면 R=S이므로 ①과 같다.
- 자동 검출의 시작 S=A라면 R=S+F가 되므로, **E와 F가 같을 때** ②와 같은 혼합·복귀 연산이다.
- 따라서 ‘고정 비율이면 ①, 자동이면 ②’라는 이름별 분기보다 **실제 안정 재료가 확보됐는지**로 판단한다. 안정 후보의 범위와 최종 loopStart/loopEnd는 따로 기록한다.

**최종 반복 길이도 같이 설계한다.** 현재 더블베이스에서 F=0.16초만큼 복귀점을 미루면 15칸 중 **9칸이 0.724~0.877초**가 된다. 7월 ADR의 0.9초 목표는 페이드 전 구간만으로 검사하면 안 된다. 준비안의 기본 선택은 검출기가 처음부터 **최종 목표 길이 + F + 정렬 여유**를 확보하도록 하는 것이다. 정렬 후 `E−R`로 목표를 다시 검사한다. 현재 정렬만으로도 한 칸이 이미 0.9초보다 짧아지는 만큼 마지막 확인이 필요하다.

충분한 안정 재료를 못 찾으면, 위상·접합·음량 검사를 통과하는 범위에서 F를 줄이는 것을 대체 방법으로 둔다. F를 줄인 뒤 R과 길이도 다시 계산한다. 그래도 목표를 못 채우면 짧은 후보를 예외로 기록하고 다른 구간/샘플을 비교한다. **0.9초는 목표이며 기존 검출기의 최소 허용 길이 0.3초와 다르다.** 부족한 길이를 채우려고 무음·어택을 끌어오거나 음높이를 바꾸지 않는다. 이 수치는 버퍼 시간이고, 실제 들리는 반복 길이 `(E−R)/playbackRate`도 별도로 확인한다.

기존 `alignLoopEndToStart`는 **S 이후와 E 이후의 30ms 창**을 비교해 끝을 ±20ms 안에서 정렬한다. R을 옮겼거나 F를 바꿨다면 기존 정렬 결과를 그대로 신뢰하지 않는다. 실제 혼합하는 `[R−F,R)`와 `[E−F,E)`의 위상·음량·채널별 결과를 다시 확인하고, 정렬 때문에 안정 구간을 벗어나거나 최종 길이가 줄지 않는지 검사한다.

더블베이스의 실제 겹침 창(최대 160ms)의 정규화 내적 중앙값은 기존 방식 −0.06, ①의 15칸 전체 +0.59다. S<F인 5칸을 빼면 **+0.69**로 재현돼, 앞선 상관값 차이는 집계 대상 차이로 확인됐다. 높은 상관만으로는 어택 재료를 써도 된다는 뜻이 아니다. 다른 악기의 ① 상관 하위 10%는 −0.82여서 역상 상쇄 검사도 계속 필요하다.

현재 sin/cos 페이드는 같은 크기·같은 위상 신호에서 중간에 **약 +3dB**를 더한다. 상관이 높을 때는 합이 1인 가중치가 유리하고, 상관이 낮을 때는 같은 가중치가 음량을 꺼뜨릴 수 있다. 실제 상관·음량에 맞는 페이드를 비교한다. 두 대안 모두 위 접합 지표를 통과했지만 페이드 음량 문제까지 해결한 것은 아니다. 예를 들어 ①의 페이드 구간 RMS는 직전 구간 대비 −4.7~+8.2dB였다. 이 값에는 원음의 세기 변화도 포함된다.

최초 준비안의 클라리넷 ‘2.39배’ 단일 샘플 차이는 근거에서 제외한다. 디코드·리샘플링·경계 선택에 민감한 값을 모든 장치에 일반화할 수 없다. 이는 같은 입력에서 무작위로 변한다는 뜻은 아니다. 위 분포 비교도 한쪽 접합 샘플의 지표이므로 페이드 진입부·복귀 직후·RMS 구멍·주기적 변조·청감을 함께 검사한다.

브라우저는 지정한 `loopEnd`에서 `loopStart`로 돌아간다. 앱의 혼합 구간에 맞춰 복귀 위치를 바꿔 주지 않는다. 잘못된 링크 앵커도 [W3C Web Audio의 Looping 정의](https://www.w3.org/TR/webaudio-1.0/#looping-AudioBufferSourceNode)로 바로잡았다. 기존 ‘버퍼가 생성되고 끝 데이터가 바뀐다’ 테스트에 실제 연속성·페이드 음량 행동 검사를 보강한다.

### 4. 가야금은 미리듣기 유출과 재생 여운 절단을 함께 고쳐야 한다

가야금은 긴 파일 속 개별 음을 `offset`/`duration`으로 구분한다. 미리듣기는 루프를 끄지만 `source.start(start, liveStartOffset)`만 호출한다. 해당 음의 `duration`을 소스 재생 한계로 전달하지 않아, 손을 떼기 전까지 뒤의 녹음을 계속 읽을 수 있다.

재현: 아래쪽 도(uiMidi 60, 목표 C4)를 30초 유지.

- 선택 구간: 원본 `127.169`초부터 `0.723`초. 현재 중심 음정보는 `cents: 16`.
- 처음에는 도가 나고 자연스럽게 줄어든다.
- **약 11.8초와 21.8초에 다음 녹음이 다시 발음**한다.
- 초기 구간의 기본음 근처 피크는 약 261.6Hz, 이후 구간에는 약 290Hz·309.5Hz와 그 배음들이 나타났다. 같은 도를 유지한 결과가 아니다.
- 샘플맵과 배속으로 계산한 다음 두 시작점은 11.76초·21.75초이고, 맵의 측정 Hz로 계산한 음높이는 약 292·310Hz다. 최초 FFT 근삿값과 구분해 기록한다.
- 추가 PCM 검사에서는 **10칸 모두 약 7.1~11.8초 사이에 다음 강한 발음**이 나왔다. 도 한 칸에 국한된 문제가 아니다.

저장 획 재생은 이미 `sampleSegmentBounds`와 `start(..., duration)`으로 제한하지만, **현재 맵의 duration은 자연 감쇠가 끝나는 위치가 아니다.** 48kHz 재측정에서 절단 직전 50ms RMS는 최초 0.5초 안의 최대 50ms RMS보다 약 22~26dB 낮았고, 이후에도 여운이 남았다. 최초 크기 대비 −40dB 아래를 250ms 유지하는 임시 기준으로 보면 **잘리는 지점 이후** 약 0.6~1.8초가 더 필요했다. 발음 시작부터 잰 총 감쇠 시간과 구분한다. 이 문턱 자체를 최종 청감 기준으로 확정하지는 않는다.

수정 계획은 **음별로 발음 시작·자연 감쇠 끝·다음 발음 전 한계·말단 페이드**를 실측하고 미리듣기와 저장 획 재생이 같이 쓰는 것이다. 기존 duration을 미리듣기에 그대로 넣는 것만으로 끝내면 안 된다. 현재 포락선과 `stop()` 시각도 함께 검토해 긴 획에서 여운이 먼저 잘리지 않게 한다. 손 떼기·짧은 획·다음 음의 여운 처리와 전체 정지/취소 시 페이드도 두 경로에 같은 규칙으로 적용한다.

`start(when, offset, duration)`의 duration은 **출력 시간 대신 소비할 버퍼 내용의 초**다. 따라서 비반복 소스의 원음 끝 제한은 이 인자로 구현할 수 있고, 배속 변화에 맞춰 종료 벽시각을 계속 추측할 필요가 없다. 원음 말단에 페이드를 적용하면 그 페이드도 배속에 따라 함께 재생된다. [W3C Web Audio 1.9.3의 start 정의](https://www.w3.org/TR/webaudio-1.0/#dom-audiobuffersourcenode-start)를 따른다. 음이 끝나도 같은 높이에서 자동으로 다시 뜯지 않는다.

### 5. 파일을 유지하면서 도착 칸의 음별 게인을 적용한다 — 확인된 보정 오류

`_scheduleSampleSourceNode`는 획 첫 음의 샘플을 계속 재생하며 배속을 바꾸지만, `connectMelodyEnv`는 각 도착 칸의 게인으로 바꾼다. 멀티샘플 드로잉의 `liveDrawingMove`에도 같은 문제가 있다. 음별 표는 해당 칸에서 선택되는 샘플을 측정한 값이므로 다른 파일에 그대로 적용할 근거가 없다.

| 한 획 안의 이동(uiMidi) | 유지되는 파일 | 예약된 음별 게인 변화 |
| --- | --- | ---: |
| 더블베이스 위쪽 레→미(74→76) | `doubleBass_D3.mp3` | 0.787→3.981, +14.1dB |
| 비올라 아래쪽 라→시(57→59) | `viola_A3.mp3` | 1.413→0.708, −6.0dB |
| 플루트 위쪽 미→파(76→77) | `flute_E6.mp3` | 1.288→0.732, −4.9dB |

재실행으로 같은 값이 나왔다. 이 수치는 **게인 계수의 비율**이며, 글라이드·필터·리미터를 거친 최종 출력의 순간 음량 차를 그대로 측정한 수치는 아니다.

**cents까지 같은 오류라고 묶지는 않는다.** 현재 배속은 유지 중인 `segment`/`sampleSegment`의 midi와 cents를 사용한다. 이 부분은 실제 소스 기준이라는 점에서 맞다. 새로 측정할 음정 보정도 실제 파일·구간에 결합해야 하며, 도착 칸의 다른 파일 보정을 대입하면 오히려 음정이 틀어진다.

단소처럼 긴 파일에서 구간을 고르는 비멀티샘플 미리듣기는 구간 변경 시 소스를 다시 만든다. 따라서 ‘모든 악기, 모든 경로에서 한 획은 무조건 첫 파일’이라는 일반화도 피하고, 악기/경로별 선택 정책을 공통 계획으로 정리한다.

**단소 아래쪽 라→미(uiMidi 57→64, 목표 A4→E5)를 필수 회귀 사례로 추가한다.** 현재 MP3를 디코드해 VM 엔진을 실행한 결과:

| 경로 | 미에 도착했을 때 쓰는 원음 구간 | 소스 수 / 배속 |
| --- | --- | --- |
| 드로잉 미리듣기 | D#5 구간(offset 17.76초, cents +28)으로 교체 | 1→2개 생성 / 약 1.042배 |
| 저장 획 재생 | 처음 고른 G#4 구간(offset 0.56초, cents +7) 유지 | 계속 1개 / 약 1.581배 |

저장 획은 첫 구간을 유지한 채 게인을 약 1.413→1.122로 바꿔 **약 −2.0dB**의 보정 변화도 만든다. 여기서도 ‘2dB’는 게인 비율이며 최종 출력 RMS를 뜻하지 않는다. 두 배속은 각자 선택한 구간에 대한 목표 음 계산으로는 맞지만, 원음의 음색과 남은 조율 오차가 다르다. 구현 검증에서는 소스 선택·재발음·게인·안정된 미의 실제 중심 음정을 함께 비교한다.

### 6. 일시정지 재개보다 플레이헤드부터 새로 재생할 때 샘플이 달라진다

일시정지 후 재개는 같은 AudioContext를 suspend/resume하므로 기존 소스를 이어간다. 반면 `seekPlan`의 `shiftStrokeSegments`는 탐색 위치의 음을 새 첫 이벤트로 만들고, 스케줄러는 그 음으로 파일을 다시 고른다.

재현: 바이올린 맨 아래 솔(55)에서 맨 위 솔(79)로 올라가는 6초 획.

- 처음부터 재생한 높은 솔: `violin_G3.mp3`의 **4.0배속**.
- 4.5초부터 재생한 높은 솔: `violin_G5.mp3`의 **1.0배속**.

두 경우 목표 MIDI는 같지만 음색·반복 길이·샘플의 잔여 조율 오차가 달라질 수 있다. 이 예시만으로 음높이 계산이 틀렸다고 단정하지 않는다. manifest의 `minRate`/`maxRate`는 선언돼 있으나 현재 샘플 배속 계산에 적용되지 않는다. **maxRate=1.9로 배속만 잘라서는 안 된다. 그렇게 하면 목표 높은 솔이 나오지 않는다.** 허용 배속 밖에서는 적절한 샘플로 연결하는 정책이 필요하다.

획의 첫 파일을 항상 유지하는 것을 보존 규칙으로 고정하지 않는다. 같은 높이는 소스를 유지하고, 음이 바뀌면 적절한 샘플로 부드럽게 연결하는 방식을 우선 검토한다. 전체 재생·미리듣기·탐색이 같은 선택 규칙을 사용해야 한다. 탐색 시에는 필요한 이전 이벤트와 진행 중인 연결 상태도 복원해, 잘린 획의 첫 음만으로 임의로 재선택하지 않도록 한다.

### 7. 자동 루프 대상과 음별 게인 허용 폭이 결합돼 있다

엔진의 `noteMelodyOutputGainLimitDb`는 `SUSTAIN_AUTO_LOOP_INSTRUMENT_IDS`에 든 악기에 ±12dB를 허용한다. 측정 도구도 `AUTO_LOOP_IDS`로 같은 결정을 한다. 따라서 바이올린을 자동 루프 대상에 추가하는 것만으로 ±3dB가 ±12dB로 넓어진다.

루프 검출 알고리즘의 대상과 음량 보정 정책을 **먼저 분리한다.** 기존 더블베이스 ±12dB 예외와 나머지 ±3dB 한도를 유지하고, 새 악기에 예외가 자동 전파되지 않게 엔진·측정 도구를 같이 고친다. 정식 구현 시에는 이 정책을 ADR로 남기고, 결합된 규칙을 적은 루트 `AGENTS.md`·`CLAUDE.md`도 반드시 함께 갱신한다. 이번 준비 작업에서는 두 지침 파일을 수정하지 않았다.

### 8. 미리듣기와 전체 재생의 국악 필터 차이도 확인됐다

대금·소금·해금은 현재 멀티샘플이다. 미리듣기의 `useFilter = !multi && !isGayageumPlan(plan)` 때문에 저역통과 필터를 건너뛰지만, 전체 재생의 `connectGugakSampleTone`은 필터를 적용한다. 주석의 ‘동일한 신호 경로’와 실제 동작이 다르다.

이는 원래 지속음 접합 결함과 별개지만 두 경로의 음색·음량 비교에 영향을 준다. 재측정에서는 필터 전/후를 구분하고, 구현 때 이 세 악기의 의도한 공통 경로를 정한다. 전체 악기의 음색을 새로 설계하는 작업으로 확대하지 않는다.

## 음높이 조사와 보존 기준

### 계산값과 실제 소리를 분리해서 검사한다

현재 **화면 칸 중심 → 저장 좌표 → 목표 MIDI 계산은 170/170칸에서 일치**했다. 이것은 파일 속 실제 음정까지 정확하다는 뜻은 아니다.

현재 맵의 `segment.midi + cents/100`을 녹음된 음높이로 간주해 재생 속도를 계산한다. 서양 맵의 다수 음은 미세 조율값이 없고, 국악의 측정값도 실제로 반복하는 구간의 중심 음정과 차이가 남을 수 있다. 옆 음 파일을 빌리는 기존 `cents`는 파일의 반음 차이까지 포함하므로 새 측정값으로 무심코 덮으면 안 된다.

실제 렌더 PCM을 여러 180ms 창으로 나눠 자기상관과 FFT 배음 추정으로 교차 확인했다. 반음은 100센트다. 아래 값은 중심 음정의 대략적인 오차이며, 자연스러운 음정 흔들림의 전체 범위가 아니다.

| 악기·화면 위치 | 목표 주파수 | 그릴 때 / 획 재생 중심 오차 | 판단 |
| --- | ---: | ---: | --- |
| 플루트 맨 위 솔 | 1567.98Hz | +40.5 / +40.6센트 | 높은 음의 원음 조율 점검 |
| 오보에 맨 위 솔 | 1567.98Hz | +36.4 / +37.6센트 | 높은 음의 원음 조율 점검 |
| 호른 맨 아래 솔 | 98.00Hz | +32.6 / +32.6센트 | 두 경로에 공통으로 남은 조율 오차 |
| 단소 아래에서 5번째 미 | 659.26Hz | −27.0 / −27.6센트 | 현재 구간에 맞는 조율값 재확인 |
| 첼로 위에서 2번째 파 | 349.23Hz | −23.6 / −22.9센트 | 원음 조율 점검 |

위 5칸은 예시일 뿐 보정 대상 전체가 아니다. 최초 자료를 재집계하면 지속음 160칸 중 중심값이 나온 159칸에서 **56칸이 ±10센트를 벗어났다**(전체 대상의 35%). 비올라 위쪽 파 1칸은 유효 중심값이 없고, 최저 솔은 유효 창이 적다. 56칸을 그대로 확정 보정 목록으로 쓰지 않는다.

- 플루트: 15칸 중 11칸 초과, 악기 전체 중앙값 약 **+14센트**. 48kHz YIN 자료도 같은 경향이다.
- 호른: 최초 9/15칸, YIN 10/15칸 초과. 전체 중앙값은 모두 약 **+11센트**로, 문턱 근처 판정과 공통 편향을 구분한다.
- YIN의 원시 결과에는 강한 배음을 기음으로 잡은 값이 있어 단순 집계는 62칸으로 나온다. 옥타브·배음 오검출 검토 없이 이 숫자를 실제 오류 수로 쓰지 않는다. 클로드의 배음 교차 검증은 실제 옥타브 오류 없음으로 보고했고, 재확인한 스펙트럼도 약한 기음과 강한 배음 문제를 지지한다. 최종 검증은 전 칸에서 넓은 탐색과 배음 검사를 함께 수행한다.

측정기의 순수 사인파 대조는 49~1568Hz에서 약 0.3센트 이내였지만, 예상 음 주변만 탐색한 분석기로는 옥타브 오류를 배제할 수 없다. 실제 악기에서는 배음·비브라토 때문에 불확실성이 더 크다. 특히 비올라 위쪽 파(uiMidi 77)와 최저 솔은 **자동 보정치 확정 보류**를 유지한다.

해금의 원래 맵 항목들은 `cents: 0`, `detectedHz`가 평균율의 명목 주파수다. 이웃 파일 재사용 항목에는 별도의 반음 보정이 추가된다. 맵의 출처와 실제 정확도는 별개다. 최초 렌더 자료를 재집계하면 해금의 중앙값은 약 **−1.3센트**, ±10센트 밖은 **1/10칸**으로 실제 음정은 대체로 맞는다. 출처가 불분명하다는 이유로 불필요한 일괄 보정을 하지 않는다. 최종 구간을 바꾼 경우에는 다시 측정해 출처·구간·신뢰도를 기록한다.

보존할 규칙:

1. 저장 좌표는 기존 서양 15칸 기준, 국악 화면은 10칸을 유지한다.
2. 국악 화면 변환은 `storedYFromDisplay`/`displayYFromStored`를 거친다. 보이는 좌표를 바로 음정 계산에 넘기지 않는다.
3. 악기별 옥타브 이동을 보존한다. 플루트·오보에·소금·단소는 +12, 첼로·호른은 −12, 더블베이스는 −24다. 같은 ‘솔’이라도 악기의 음역은 다르다.
4. 연주할 목표 음, 선택한 파일의 실제 기본음, 파일 재사용 보정값을 분리해 기록한다.
5. 먼저 지속 구간 후보를 정하고 **그 구간의** 음정을 측정한다. 이후 접합·배속 적용 결과에서도 다시 측정한다.
6. 낮은 음에서 출발해 위로 올라온 경우, 처음부터 높은 음에서 시작한 경우, 해당 위치부터 재생한 경우를 비교한다. 실제 소스 선택·보정·음 연결을 공통 계획으로 검사한다.
7. 보정은 실제 파일과 사용 구간에 연결한다. 같은 파일을 다른 칸에 빌려 쓰더라도 실제 중심 주파수는 하나이고, 목표 칸만 달라진다. 목표 Hz / 실제 소스 중심 Hz로 필요한 배속을 구하며 기존 이웃 음 차이를 중복 보정하지 않는다.

## 다음 구현의 작업 순서

실행 순서는 **기준 고정 → 독립 결함 수정 → 소스 전환 설계 → 지속 구간 확대 → 음정 보정 → 음량 보정·최종 검증**이다. 접합 클릭이 남은 상태로 소스 전환의 청감을 판단하지 않는다. 각 단계의 국소 회귀 검사는 바로 수행하고, 최종 구간에 의존하는 보정표 재측정은 뒤에서 한다.

### A. 기준 데이터와 재현을 고정

170칸의 화면 위치·목표 Hz·물리적 소스(파일+구간)·기존 cents·게인·반복 구간을 기록한다. 샘플레이트·디코더·채널·분석 창·신뢰도·원본 식별값도 남긴다. 단일 수평 획 외에 위 게인 이동 사례, 단소 라→미의 경로 차이, 2옥타브 도약, 플레이헤드 재생, 가야금 30초 유지를 회귀 사례로 포함한다. 안정 구간 범위·앞 재료·최종 반복 길이도 별도 기록한다.

실제 MP3를 쓰는 현재 진단을 재현 가능한 도구로 정리한다. 노드 스텁 테스트는 계획과 수명 확인에 쓰고, 실제 렌더·청감 결과와 구분한다.

### B. 소스 전환과 독립적인 결함부터 수정

1. **게인 한도 분리:** 자동 루프 명단과 음별 게인 허용 폭을 엔진·측정 도구에서 분리한다. 더블베이스 ±12dB, 그 외 ±3dB를 유지하고 루프 확대만으로 한도가 바뀌지 않음을 검사한다.
2. **공통 접합 수정:** 앞·끝 재료를 안정 구간 안에 두고, 실제 복귀점과 일치하게 섞는다. 현재 자동 검출 악기부터 목표 길이+페이드+정렬 여유를 고려하고 최종 반복 길이를 재검사한다. 160칸에서 접합·위상·페이드 음량을 확인한다. 이 단계에서 자동 검출 악기 명단을 일괄 확대하지 않는다.
3. **가야금 구간과 감쇠:** 각 실제 음의 자연 감쇠 끝과 다음 발음 전 한계를 측정하고 말단 페이드를 정한다. 미리듣기·저장 획·내보내기의 구간 제한과 포락선에 같이 적용한다. 현재 맵의 짧은 duration만 복사하지 않는다. 파일을 빌려 쓰는 칸은 같은 원음 경계를 쓰되 배속에 따른 출력 여운을 검사한다. 같은 높이에서 자동 재발음하지 않으며 지속 루프에는 넣지 않는다.

세 항목은 소스 전환 재설계가 끝나기를 기다릴 필요가 없다. 다만 접합 수정을 복귀점 한 줄 변경으로 끝내지 않고 재료·최종 길이·음량 조건까지 확인한다.

### C. 소스 선택·보정의 공통 경로를 설계

`audio-plan.js`에서 목표 음, 선택한 실제 소스, 그 소스의 음정·음량 보정을 함께 결정하도록 준비한다. 관악기·활 현악기는 **같은 음은 유지하고, 음 변경 시 적합한 샘플로 짧게 겹쳐 연결하는 방식**을 우선 시제품으로 비교한다. 새 샘플의 어택을 매번 다시 들려주지 않도록 지속 구간에서 연결하고, 각 소스에는 자기 보정값을 적용한다. 현재 파일을 유지하는 구간에는 도착 칸의 다른 파일용 게인을 넣지 않는다. 배속별 추가 음량 보정이 필요하면 실제 소스·배속 조합을 측정한 근거를 사용한다. 가야금은 새 음을 뜯는 발음과 B 단계의 감쇠 규칙을 따른다.

음 이동·큰 도약·빠른 왕복·파일 로딩 지연에서 목표 음과 연속성을 함께 보장해야 한다. 미리 로드할 샘플, 로딩 중 기존 소스로 목표 음을 유지하는 대체 처리, 취소된 로딩의 뒤늦은 발음 방지를 포함한다. 배속 한도는 샘플 선택에 반영하고 음높이를 희생하는 단순 clamp는 사용하지 않는다. 탐색은 전체 이벤트 기준 선택·전환 상태를 복원한다. **단소 라→미의 미리듣기/저장 획 차이**도 이 단계에서 해소한다. 정책을 확정한 뒤 E·F의 새 보정표를 만든다.

### D. 지속 구간 재선정과 자동 검출 적용을 확대

B의 접합 규칙을 적용한 상태에서 바이올린·비올라부터 안정적인 원음 몸통을 선택하고 나머지 악기로 확대한다. 검출기가 충분한 앞 재료와 페이드 후 목표 길이를 같이 확보하도록 한다. 모든 지속음에서 공통 검증을 적용하되, 후보를 못 찾을 때는 더 짧은 F·다른 후보·다른 샘플 순으로 비교하고 목표 미달은 명시한다. 검증 없이 기존 고정 비율로 돌아가도 합격으로 간주하지 않는다.

짧은 원음·다채널·큰 배속에서 실제 들리는 반복 길이와 페이드도 확인한다. 루프 길이를 늘리려고 배속을 임의로 바꾸지 않는다. 엔진의 `continuousSustainPlan`과 측정 도구가 같은 최종 구간·혼합 결과를 사용하게 한다.

순수 계산은 `music-core.js`/`audio-plan.js`, Web Audio 그래프·수명은 `audio-engine.js`/`audio-node-scope.js`에 둔다. 확정된 설계 변경은 새 ADR와 필요한 쌍의 `AGENTS.md`·`CLAUDE.md`에 반영한다.

### E. 확정 구간의 중심 음정과 출처를 보정

배음·옥타브 오검출을 교차 검사한 뒤 실제 루프와 가야금 발음의 중심값을 측정한다. 플루트·호른처럼 같은 방향의 편향이 있는 악기는 **악기 공통 편향 + 실제 소스별 잔차**로 분석한다. 공통 보정을 먼저 적용한 뒤 잔차를 계산해야 중복 보정을 피할 수 있다. 같은 파일을 빌려 쓰는 칸에는 중복 가중을 주지 않는다.

이 분해는 유용한 측정·관리 방식이지만, 런타임에 반드시 두 표를 따로 둘 필요는 없다. 파일/구간별 최종 실제 음정을 생성해 사용하는 방식도 가능하다. 어느 표현이든 기존 cents의 반음 재사용 정보와 실측 잔차를 구분하고, 불확실한 음은 자동으로 확정하지 않는다. 드로잉·전체 재생·탐색·내보내기에 같은 계산을 적용한다.

서양 맵은 `tools/curate-western-samples.py`의 생성 파일이다. 이 환경에서는 기본 원본 경로 `C:/game/선율-서양(philharmonia)`가 없고 `PHILHARMONIA_RAW_BASE`도 설정돼 있지 않아, **원본 아카이브로 전체 큐레이션을 재생성하는 작업은 지금 재현할 수 없다.** 이것이 현재 MP3의 조율 측정을 막지는 않는다. git에 포함된 MP3에서 보정 메타데이터를 재현 가능하게 생성하고, 나중에 원본 큐레이션을 다시 해도 보정이 사라지지 않게 생성 절차에 연결한다.

### F. 음량 재측정과 브라우저·청감 검증

최종 소스·구간·페이드·필터가 정해진 뒤 `npm run measure:loudness -- --notes`를 실행하고 음별/악기별 게인을 갱신한다. 측정 도구도 실제 엔진 구간을 사용해야 한다. 자동 루프 대상 확대가 보정 한도를 바꾸지 않음을 확인한다.

소스 연결 중에는 두 소스 각각의 보정과 전환 곡선을 함께 측정한다. 자연스러운 강약·비브라토·시김새를 보존한 상태로 변경 전후를 듣고, 최종 마스터/리미터를 거친 전체 듣기와 WebM도 비교한다. 실제 브라우저의 샘플레이트와 필터 차이를 측정 기록에 남긴다.
