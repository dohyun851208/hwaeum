# 채널 이원화 + 2차 비밀번호(점유)

확인일: 2026-06-28

## 결론

학급 채널을 **두 층위로 이원화**하고, 채널마다 **2차 비밀번호**로 점유·접근을 통제한다.

- **본질 채널(고유번호)** — 지금처럼 숫자(최대 6자리). URL·저장 경로의 진짜 주소이며 **절대 바뀌지 않는다.** 학생이 접근할 때 항상 이 숫자를 쓴다.
- **표시 명칭(displayName)** — 상단에 보이는 한글 이름(예: "3반 봄 음악"). 교사가 바꿀 수 있고, 본질 채널 번호는 그대로다.

권한 게이트:

| 행동 | 필요한 것 |
| --- | --- |
| 채널 생성 · 표시 이름/2차 비번 설정 | 1차 관리자 PIN(8624) |
| 작품 공유(올리기) | 채널 번호 + 2차 비밀번호 |
| 채널 열람(보기) | 채널 번호 + 2차 비밀번호 |
| 작품 삭제 | 본인 작품 또는 1차 PIN(8624) (기존과 동일) |

점유: 교사가 2차 비밀번호를 설정하면 그 채널은 그 교사(ownerHash)가 **점유**한다. 이후 다른 교사는 같은 번호를 만들거나 2차 비번을 덮어쓸 수 없다. 기존에 이미 작품만 올라가 있던(채널 레코드 없는) 번호는 **먼저 8624로 점유하는 교사가 소유자**가 된다. 2차 비밀번호는 **숫자만**(4자리 이상).

## 비교

| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 채널 = 같은 번호 작품들의 묶음(레코드 없음, 종전) | 단순. 누구나 아무 번호로 공유 | 이름도 못 붙이고, 점유·비공개가 불가능 | 폐기 |
| 채널 단위 레코드(`channel.json`) 신설 | 표시 이름·소유자·2차 비번을 담아 점유/접근 통제 가능 | 채널 생성 단계(관리자)가 새로 필요 | 채택 |

## 적용 방향

- **데이터 모델**: `share/channels/{번호}/channel.json` 한 개를 새로 둔다. 필드: `channel, displayName, ownerHash(sha256 ownerKey), passHash(sha256 "번호:비번"), createdAt, updatedAt`. **2차 비번은 평문 저장 금지** — 채널 번호로 소금 친 해시만 저장(`_utils.cjs`의 `hashPass`). 클라이언트로 보낼 땐 `sanitizeChannelMeta`로 owner/pass 해시를 제거하고 `hasPass`만 알린다.
- **서버 API**:
  - 신규 `POST /api/share/channel-claim` — 8624 검증 → 미점유면 생성, 내가 소유자면 이름/비번 수정, 남이 점유했으면 403.
  - `GET /api/share/channel` — `passHash`가 있으면 `?pass=` 일치할 때만 작품 목록을 주고, 아니면 `locked:true`(작품 0개).
  - `POST /api/share/publish` — 채널이 점유돼 있고 2차 비번이 맞아야 허용. 미점유 채널은 **409**로 거절(404는 클라이언트가 "API 없음 → 로컬 폴백" 신호로 쓰므로 충돌 방지).
- **강제 범위**: 교차-교사 점유 강제는 **Vercel 배포(서버)** 기준. `npm run serve`(파이썬 정적 서버)는 `/api/*`가 없어 `share-store.js`가 IndexedDB로 폴백하므로, 로컬은 **같은 브라우저 안에서만** 점유/비번을 흉내 낸다(단일 PC 테스트용). 로컬 폴백의 1차 PIN 검문은 `share-store.js`의 `LOCAL_ADMIN_PIN`이 담당한다.
- **클라이언트**: `share-store.js`에 `claimChannel`·`rememberPass/loadPass`·pass 인자(`listChannel`,`publishWork`) 추가. 공유탭(Step 5)에 관리자 채널 생성/관리 폼, 완성탭(Step 4) 공유 시 2차 비번 입력, `channel.html`에 비번 게이트 + 표시 이름 인라인 수정.
